# ADR 0005: Report Scope and Conservative Impact

Status: Accepted
Date: 2026-08-02

## Context

Research evidence may come from task-local code that is never merged to main.
A single validated_through commit incorrectly assumes the evidence commit is an
ancestor of main. Path dependencies can also omit real semantic dependencies.

## Decision

Every Report separates evidence validity from applicability and declares:

- claim_scope as snapshot or baseline;
- evidence tree and immutable RunResult;
- accepted-at main tree;
- validation basis for baseline claims;
- reviewed code, input, environment, and resource dependencies.

Snapshot claims remain historical facts when main advances. Baseline claims
enter impact_pending when their validation basis is behind. Impact is evaluated
against each report basis, not only the latest push range.

Effective applicability is derived at read time. A full Git tree mismatch alone
is insufficient because accepting protocol records under `.research/**` changes
the tree that contains the Report itself. The read model therefore returns
current when the difference is protocol-only, returns impact_pending for any
governed non-protocol change, and fails an unavailable basis closed as
impact_pending. Stored stale, superseded, and snapshot-only states are never
upgraded by this derivation.

No-overlap means only that declared dependencies did not overlap. The MVP never
automatically advances validity. Impact PRs use an expected Report revision and
must be regenerated against current main before merge.

Impact analysis and manager disposition are separate records. An accepted
`ReportImpact` binds analyzer evidence and may conservatively materialize stale
or a human-reviewed no-overlap basis advance. A later `ImpactDecision` records
one explicit manager choice: rerun, waive, keep stale, invalidate, or correct
dependencies. The Decision binds the accepted Impact digest, exact current
Report/base, reviewer, reason, and disposition inputs. Its derived PR is
protected-base regenerated before merge. Rerun only references an accepted
planned/ready Task and never starts a Run; dependency correction stays stale;
waiver preserves the original evidence tree while advancing validation basis.

The first implementation treats a merge as a typed Git code-path event. Exact
paths and a trailing `/**` segment prefix are supported; other glob syntax and
`.research` control paths are rejected. External resource/environment evidence
uses digest-bound `DependencyChangeReceipt` records. Missing or `unknown`
observations are never inferred as unchanged from a Git path miss. A path or
external overlap can produce a reviewed stale revision. A no-overlap validity
advance requires complete known coverage; snapshot Reports remain outside this
workflow.

Each accepted main push invokes the trusted `ci impact` entry point. It scans
all Reports from their individual validation bases and creates at most one
digest-bound batch PR. Push-range `before` identifies the trigger and proves
lineage; it is not substituted for any Report basis. No proposals terminate
before Git/GitHub mutation. Stable event-derived IDs, generated bytes, commit
timestamps, branch, and PR make retries converge across clean runners, and
protected-base CI repeats the complete scan before accepting the exact head.

The manager role is authenticated authority, not a synonym for an Agent or
model. In the local composition it is normally the researcher using the trusted
OS identity. A review Agent may produce advice in a background subagent, but it
retains ordinary Agent authority unless a separate, explicitly delegated and
audited credential and policy are introduced.

## Consequences

Accepting isolated experimental code remains possible without pretending that
the result describes current main. False negatives remain a reviewed governance
risk instead of being hidden by automatic validation advancement.
